Horizon module

abfs-data

Persistent ABFS platform data: license GCP service account and Kubernetes Secret, Spanner instance/database, underlying GCS bucket. Workflows for ABFS license import and clear operations. Enable this module and import valid ABFS license before enabling ABFS service and client modules.

Catalog

Module name abfs-data. No hard dependencies. autoDisableWhenUnused is false, so the module stays enabled until you disable it explicitly.

Enable order abfs-data → import license → service → client modules.

Data resources

Child app mod-abfs-data-sa deploys Config Connector resources in horizon: IAM service account abfs-license@<project>.iam.gserviceaccount.com, Secret abfs-license (key license), Spanner instance and database abfs (regional-<region>, ABFS schema applied at create; do not change DDL after first apply), and GCS bucket <projectID>-abfs.

On disable, the Secret is pruned. Spanner and GCS Kubernetes CRs are pruned; the GCP instance, database, and bucket are abandoned (data stays; they keep billing until deleted in GCP). The GCP SA is soft-deleted (~30 days). ConfigMap abfs-license-sa-identity (uniqueId, email) is not Helm-owned and survives prune so re-enable can undelete the same SA. If undelete cannot restore that identity, re-enable fails until uniqueId is cleared by hand (new SA needs a new Google license). Project ID comes from Module Manager config.

Horizon catalog

Child app mod-abfs-data-license-workflows exposes abfs-license-import and abfs-license-clear; mod-abfs-data-uploader-config exposes abfs-uploader-config-select (which Android revision the uploaders seed, table in ConfigMap horizon/abfs-uploader-config); mod-abfs-data-spanner-workflows exposes abfs-spanner-backup-schedule. They appear under Workflow Templates when the module is READY.

Import verifies the payload, then writes or replaces license. Run import again to update a license that is already stored. Clear empties the value but keeps the Secret (confirm=yes). if abfs-data-server-node-pool and/or abfs-data-uploader-node-pool already exists, each workflow deletes those KCC ContainerNodePool resources so Argo recreates them with create-time GCE metadata from the Secret (KCC metadata is immutable; gcloud node-pools update --metadata does not exist). ABFS client node pools are not deleted. Import the license before enabling abfs-service module, as it removes the need to recreate the node pools. Portal submit needs Argo Events Sensors in argo-events; argo submit works without them.

Steps to verify correct license import

After Portal abfs-license-import (or argo submit), confirm the Secret in the cluster:

kubectl get secret abfs-license -n horizon -o jsonpath='{.data.license}' | base64 -d | head -c 80; echo

License gate Empty data.license means import did not land — re-run import before enabling abfs-service-module (PreSync validator will fail sync otherwise).
